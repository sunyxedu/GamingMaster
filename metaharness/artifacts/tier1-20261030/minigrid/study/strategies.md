# Strong-play strategies for MiniGrid / BabyAI

Source links are verification targets. Algorithm and model-role recommendations below are proposed engineering choices, not measured winning rates or claims of a community consensus. MiniGrid is a benchmark, not a competitive game: there are no opponents, build orders, or combat counters; the relevant counters address task traps and partial observability.

MiniGrid rewards solving a generated symbolic puzzle under a step budget, while BabyAI adds a natural-language mission and a strict verifier. The primary references are the [MiniGrid documentation](https://minigrid.farama.org/), [environment source](https://github.com/Farama-Foundation/Minigrid/tree/master/minigrid/envs), [BabyAI verifier](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/babyai/core/verifier.py), the BabyAI paper ([Chevalier-Boisvert et al., 2019](https://arxiv.org/abs/1810.08272)), and the MiniGrid benchmark paper ([Chevalier-Boisvert et al., 2023](https://arxiv.org/abs/2306.13831)).

## General execution policy

1. Parse the mission into typed predicates: target object attributes (type, color), required relation (go-to, pick-up, open, put-next), ordering, and any repeated sub-instruction. **Astra prompt:** ask for a short precondition/postcondition plan and a current subgoal. **Code:** keep a mission state machine and action legality checks. **Jev question:** “Which visible object satisfies predicate X?” with a small enum answer.
2. Maintain an egocentric map from observations and turns. Mark walls, doors, hazards, visited cells, object identities, and the agent pose; unknown is distinct from empty. **Code:** coordinate transforms, map bookkeeping, and shortest-path search. **Astra prompt:** choose exploration when the target is not known and revise the map after each observation. **Jev question:** classify each visible cell as wall/open/door/key/target/hazard/unknown.
3. Plan paths with turns included. Before every forward action check the cell ahead; rotate in place to align, then move. Prefer the shortest known safe route and reserve steps for mandatory interactions. **Code:** BFS/A* over known traversable cells with turn cost and carried-object constraints. **Astra prompt:** select which frontier to explore when several routes are possible. **Jev question:** “Is forward safe and legal now?”
4. Interact only when adjacent and facing the object. For pickup, ensure the hand is empty; for drop, ensure the destination is empty and satisfies the verifier; for toggle, distinguish a door from a box. Every failed interaction costs a step. **Code:** precondition checks and action validation. **Astra prompt:** reason about the order of key, door, box, and placement subgoals. **Jev question:** select the legal interaction among `{pickup, drop, toggle, none}`.
5. Stop immediately on success or failure flags. Do not issue `done` as a guess; base MiniGrid usually treats it as an action with no generic success meaning. **Code:** termination handling and score accounting. **Astra prompt:** verify the mission's final condition from the latest observation. **Jev question:** yes/no “Does the latest state satisfy the final predicate?”

## Environment families and useful openings

| Family/task pattern | Strong approach and failure modes | Where to implement |
|---|---|---|
| **Empty / goal navigation / BabyAI GoTo** | A base goal-tile task requires entering the goal cell. BabyAI GoTo normally requires the named object to occupy the cell immediately in front of the agent. MiniGrid GoToObject/GoToDoor are separate tasks whose `done` semantics must be audited. Explore until the target is localized, then route to the correct terminal pose for this ID. | Code for pathfinding and task-specific terminal predicates; Astra for mission interpretation; Jev for ambiguous target recognition. |
| **DoorKey / Unlock** | Find the matching key, pick it up, navigate to the matching locked door, face it, and toggle. Keep the key until the door is opened; do not waste turns trying to walk through a closed door. A key color must match the door color. | Code for inventory and door/key predicates; Astra for route/order under partial visibility; Jev for visible key/door color classification. |
| **MultiRoom / RoomGrid** | Treat doors as graph edges. Explore a room systematically, record doorway orientation and already visited branches, and backtrack rather than repeatedly sweeping the same corridor. Open only the door needed for the current route when step budget is tight. | Code for room/frontier graph and duplicate-visit avoidance; Astra for selecting the next frontier; Jev for “which doorway/room contains the target?” |
| **LavaGap / lava hazards** | Lava is fatal. Infer the safe crossing and do not step onto an unverified lava cell; use walls and the visible gap to align before moving. A one-cell misalignment can end the episode. | Code for hazard mask and forward safety veto; Astra for choosing a crossing route; Jev for fast hazard classification. |
| **DynamicObstacles** | Obstacles update on environment steps, including turns. Audit update/collision order: a currently clear cell is not necessarily safe after the obstacle moves. Re-observe each step, prefer clearance and detours, and respect the restricted action space. There is no wall-clock advantage to thinking faster. | Code for task-specific collision/risk rules and re-planning; Astra for detours; Jev can label current occupancy but cannot certify stochastic future safety. |
| **KeyCorridor / blocked corridors** | Carrying a key or box can be necessary to enter a corridor, and narrow corridors may force a precise order. Avoid dropping an object in a dead-end unless the mission requires it. | Code for capacity and dead-end detection; Astra for ordering; Jev for identifying the only legal next interaction. |
| **Box / UnlockPickup / PutNext** | Boxes may need toggling to reveal contents; “pick up” requires actually carrying the item; “put next” normally requires cardinal adjacency to the referenced object. Check that the destination cell is empty and that the carried object is the required one. | Code for carried-object and placement preconditions; Astra for multi-step dependency planning; Jev for object/relation recognition. |
| **Memory / see-through / hidden-object tasks** | Record a cue (color, object, room, or order) when visible, then use it after moving out of view. Do not treat an occluded cell as empty. | Code for persistent memory keyed by map coordinates/objects; Astra for recalling and applying the cue; Jev for extracting the cue from an observation. |
| **BabyAI instruction levels** | Parse composition explicitly: `A, then B` requires A before B; `A after you B` requires B before A; `A and B` normally requires both without a fixed order. Check strict verifier options before touching later targets. Merely reaching the final object does not establish earlier pickup/open/placement events. | Code for a verifier-aligned subgoal state machine; Astra for parsing and selecting order where allowed; Jev for predicate recognition, never final authoritative success. |

## Search and bookkeeping priorities

Use deterministic BFS/A* over the discovered symbolic map rather than asking a model to count every turn. For navigation include orientation in the search state (`cell, direction`); for manipulation also track inventory, relevant door states, moved objects, and subgoal phase, or decompose into navigation and interaction subproblems. Replan after each material observation, door opening, or dynamic obstacle update. Include every required interaction in the remaining-cost estimate, then add exploration slack; a fixed one-turn reserve is inadequate for a key-door-pickup sequence. A Manhattan distance alone ignores walls, turning, and manipulation and is only a lower bound. These are recommended search methods, grounded in the discrete transition rules, not a requirement to train an RL policy.

When multiple objects match the mission's color/type, first satisfy every location qualifier; only then use reachability/cost as tie-breakers among truly equivalent candidates. Never overwrite an earlier map fact with “empty” from an occluded view. Treat an action that has no visible effect as consumed and investigate the new state rather than repeating it blindly. These are exact rules suitable for code; Astra should handle ambiguity and unexpected layouts; Jev should answer bounded recognition questions, never invent a route or perform arithmetic.

## Verifier-aware tactics and worked plans

The following planning rules reference the [BabyAI verifier](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/babyai/core/verifier.py), [RoomGrid level logic](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/babyai/core/roomgrid_level.py), and [world objects](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/core/world_object.py). Exact strict/done modes and object-description matching require a release audit.

- **Resolve relative language once.** Descriptions such as “on your left” in BabyAI commonly refer to initial agent-relative object sets, not whichever objects happen to be on the agent's left after it turns. Preserve the initial pose frame and mark candidates as they become visible. Astra parses the phrase; code resolves its predicate in that frame. Do not read the verifier's hidden target set into the agent state.
- **Go to the red ball:** enumerate visible/remembered red balls satisfying all qualifiers; choose a reachable cardinal-neighbor pose facing an eligible ball; finish facing it. Do not pick it up merely because pickup is available. Code computes candidate approach poses and routes. Astra chooses a new exploration subgoal if all candidates are unknown. Refer to `GoToInstr` for exact success.
- **Pick up the blue key:** free the hand if needed, navigate to a neighboring pose, face the key, and pickup. Verify inventory changed. In strict task modes picking up a wrong object can fail, so wrong-object pickup is not harmless exploration. Code owns the inventory transition; Astra chooses a safe temporary storage cell when the hand is occupied.
- **Open the red door:** if locked, obtain a red key first; navigate, face, and toggle. Distinguish an opening event from merely standing next to an already open door. An incidental early opening can interfere with later ordered tasks; plan dependencies before toggling mission doors. Standard unlocking retains the key, which matters for the next pickup.
- **DoorKey versus UnlockPickup:** DoorKey usually continues through the opened door to a goal tile; UnlockPickup requires the target pickup. In the latter, place the retained key in a reachable empty cell outside the doorway/route before trying to pick up the target. A plan that ends at unlocking is incomplete. Code checks carrying capacity and connectivity; Astra chooses the parking location. See [DoorKey](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/doorkey.py) and [UnlockPickup](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/unlockpickup.py).
- **Put the red ball next to the blue box:** the ball is the movable operand, the box is the reference. Enumerate empty cardinal neighbors of the reference and reachable approach poses from which a drop will fill one. Choose a placement that does not block the route; pickup the ball and navigate while carrying it, then drop and verify the event. Diagonal adjacency and holding the ball while standing next to the box do not substitute for the required placement. Code computes empty-cell/drop reachability; Astra handles blockages and staging. Toggle a box only if revealing its contents is part of the plan: doing so changes/removes the reference object.
- **Composition examples:** “open the red door, then pick up the blue ball” means open first; “open the red door after you pick up the blue ball” means pickup first. `A and B` normally lets the planner choose an efficient order, but both verified completions are required. Some strict sequence modes reject completing a later instruction too early. Astra produces the dependency structure; code tracks completion evidence without exposing private verifier state. Do not universally force left-to-right execution.
- **Exploration opening:** parse the mission and inventory first, inspect the initial view, then turn only when a new view is useful. Select a reachable observation frontier rather than blindly spin every four steps. Prefer frontiers/doors that may reveal a target or required key; record checked branches. Code scores travel/turn cost and map coverage; Astra chooses among semantic priorities. Avoid a blanket “never enter unknown” rule that freezes exploration: reveal uncertain cells from safe poses, and audit visibility/hazard rules for the chosen family.
- **Memory opening:** record the cue before leaving it, and associate later branches with the matching object. A branch may terminate the episode upon entry, so obtain enough evidence before committing. Code stores the cue and branch candidates; Astra chooses the matching route. See [Memory](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/memory.py).

For deterministic static tasks, manipulation-free shortest paths on the known map can be exact. An overall optimal plan cannot be guaranteed before exploration exposes the layout. In dynamic tasks observed positions can become stale; label route risk rather than claiming certainty from a one-frame view. If motion cannot be inferred reliably from the observation and action, preserve pose uncertainty rather than adding a fictitious successful forward step.

## Common mistakes and counters

- **Wrong target:** selecting the first red object when the mission says red key, red ball, or a particular room. Counter: typed object predicates and a Jev classification question.
- **Off-by-one interaction:** stopping on the target instead of adjacent and facing it, or toggling while facing the wrong cell. Counter: code-level adjacency/orientation checks and Astra's final-condition review.
- **Door/key deadlock:** trying to pass a locked door, dropping the only key, or carrying the wrong color. Counter: inventory preconditions and a key-door matching table.
- **Hazard death:** treating lava or unseen cells as ordinary floor. Counter: safety veto in code; require explicit observation before forward into a risky cell.
- **Repeated exploration:** turning around in a corridor or reopening already checked rooms. Counter: persistent map/frontier bookkeeping.
- **Ignoring the budget:** finding the goal after spending all steps. Counter: turn-aware shortest paths, reserve steps for interactions, and report remaining steps.
- **Premature completion:** using `done` or stopping after a visually plausible state before the BabyAI verifier event. Counter: explicit subgoal state machine and terminal-success extraction.

## Prompt/Jev interface contract

Astra should receive the mission, decoded visible grid, orientation, carried object, step count/budget, known map summary, and the last action/result. It should return one action from the installed enum plus a brief rationale and updated subgoal; the harness validates the action and ignores prose for control. Prompt priorities: satisfy the exact mission, preserve subgoal ordering and initial-frame qualifiers, minimize actions after ensuring success, and reassess after an unexpected result. A short persistent plan and observed map facts are more useful than re-reading an entire transcript at every step.

Jev is optional for tier 1. Decoding symbolic cell triples, checking a key color, computing adjacency, and counting steps are exact code tasks and should not require a model. Where language-to-object matching is ambiguous, send compact JSON and independent typed questions, for example `candidate_id: {c1,c2,none,unknown}`, `mission_relation: {goto,pickup,open,putnext,unknown}`, or `description_match: {yes,no,unknown}`. Supply code-computed relation facts if asking Jev to choose among them. Jev must not calculate a route, count actions, infer hidden cells, or declare authoritative success; code and environment flags remain decisive. Deterministic legality and hazard checks should be enforced in code even if Jev disagrees. Do not add a continuously running Jev action loop to a game that waits for input.
