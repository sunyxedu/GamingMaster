Minecraft: Java Edition — adaptor interface specification

Researched 2026-09-21. This document specifies a future adaptor; it contains no implemented game-playing logic. All proposed files, downloads, caches, worlds, and logs belong under `<repo>/runs/r7-minecraft/study/`. Treat timings and resource budgets below as engineering estimates until measured.

**Choose Mineflayer through a persistent Node bridge, connected to an adaptor-owned vanilla 1.21.1 server on loopback.** Python 3.14.5 owns the lifecycle and sends JSON Lines over subprocess pipes. Node owns the connected player and uninterrupted physics. The server uses `online-mode=false`; the bot uses `auth: 'offline'`. No Microsoft/Mojang account, launcher, access token, API key, renderer, or paid hosting is technically required for this connection. The mature Mineflayer API supplies world, inventory, movement, digging, crafting, and entity abstractions that a raw protocol client would have to rebuild. [Mineflayer project](https://github.com/PrismarineJS/mineflayer), [offline protocol login](https://github.com/PrismarineJS/node-minecraft-protocol).

**Practical interface alternatives.** Latency refers to expected local responsiveness, not measured benchmarks. All choices still need a legal Minecraft installation/server where applicable. Bot use on unrelated public servers depends on their rules; this study only proposes a private loopback server.

**Files and installation procedure for the adaptor phase.** Create `runtime/bridge/`, `runtime/npm-cache/`, `runtime/downloads/`, `runtime/jdk-21/`, `runtime/baselines/`, `runtime/episodes/`, and `runtime/logs/` under this study directory. Set subprocess working directories explicitly. Keep npm cache/tmp files here as well; no global npm installs or Homebrew changes.

1. Create a private Node package in `runtime/bridge/`. Install the three exact direct dependencies above with npm `--save-exact`, using `--cache` pointing to `runtime/npm-cache/`. Save package-lock.json, then use `npm ci` for reproduction. Inspect `npm ls` for incompatible/duplicate major protocol/physics dependencies. Record the effective versions, not only direct pins.
2. Download the JDK 21 archive matching `uname -m` and the OS; verify the distributor checksum and extract under runtime. On macOS the executable may be inside `Contents/Home/bin/java`; discover the actual path. Run that exact executable's `-version`.
3. Download the official 1.21.1 server JAR. The alternative automated discovery route is Mojang's `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json`: choose id 1.21.1, follow its version JSON, then `downloads.server.url`; verify `downloads.server.sha1` and record a local SHA-256. The manifest endpoint could not be fetched by this study tool; the official release article is the verified fallback. Do not invent a hash or redistribute the server JAR in source-control artifacts.
4. In a fresh episode directory, write `eula.txt` containing `eula=true` as part of the authorized server setup, subject to the operator's compliance with Mojang's EULA. This study itself neither downloaded nor accepted it. The official server is free to download; offline login is a technical server option, not evidence of a waiver of licensing terms. [Download terms](https://www.minecraft.net/en-us/download/server), [EULA](https://www.minecraft.net/en-us/eula).
5. Write the properties below **before** launching. Use a generated local port; substitute a signed decimal world seed. No public network binding, port forwarding, Microsoft login, or RCON password is needed.

```properties
server-ip=127.0.0.1
server-port=<allocated-local-port>
online-mode=false
enforce-secure-profile=false
gamemode=survival
force-gamemode=true
difficulty=normal
hardcore=false
max-players=1
pvp=false
spawn-protection=0
level-name=world
level-seed=<signed-decimal-seed>
level-type=minecraft:normal
generate-structures=true
view-distance=6
simulation-distance=5
enable-rcon=false
enable-query=false
enable-command-block=false
white-list=false
player-idle-timeout=0
allow-flight=false
```

These are settings selected for the benchmark, not a copy of default configuration. Preserve vanilla tick speed and physics. Do not copy newer properties from current documentation indiscriminately into this historical version. Offline authentication has no identity protection, which is why the adaptor must enforce the loopback bind. `spawn-protection=0` prevents protected spawn terrain from breaking ordinary gathering; `enforce-secure-profile=false` avoids requiring signed account profiles. [Property meanings](https://docs.papermc.io/paper/reference/server-properties/).

**Lifecycle and reset contract.** A Python `reset(seed)` must launch/restore the world, start Node, wait for a playable observation, and start the scored clock only at the end. It must not return merely because a TCP port opened.

1. Stop any owned prior bot/server, cancel outstanding actions, and fully drain/wait for processes. Use only PIDs/handles created by this adaptor. Never kill all Java processes. A `close()` operation must be safe to call repeatedly and after partial startup failure.
2. Map the evaluator seed using a stable digest, e.g. SHA-256 of a versioned prefix and seed string. Derive independent signed-64-bit world seed, start-time stratum and spawn tie-breaker. Send world seeds as **decimal strings** across JSON; arbitrary int64 values are not safe JavaScript Numbers. Do not use Python's randomized built-in hash.
3. Prefer a pristine, stopped per-seed baseline world copied into a fresh episode directory. A first encounter with a seed may require generating that baseline; cache its manifest. Fresh-world generation is the fallback. Never reuse the played world or merely edit `level-seed`: existing chunks, inventory, entities, stats and advancements persist.
4. Start Java with owned stdin/stdout/stderr, working directory = episode directory, arguments equivalent to `java -Xms512M -Xmx2G -jar <server.jar> nogui`. Reserve roughly 3–4 GiB overall as an initial budget and measure actual use. Continuously drain output to log files. Wait for the server's `Done (...)!` startup line and absence of a fatal error, with a cold-start budget such as 120 seconds, separately reported from play.
5. Use server stdin commands (no leading slash needed) for controlled setup: `difficulty normal`, `gamerule keepInventory false`, `gamerule doImmediateRespawn false`, `gamerule doDaylightCycle true`, `gamerule doMobSpawning true`, `gamerule naturalRegeneration true`, `gamerule spawnRadius 0`, and `weather clear`. Keep normal randomTickSpeed. Set `time set 1000` or `time set 9000` only at the final start barrier. Do not expose these commands as policy actions.
6. Create the Mineflayer bot with explicit host/port/version/username, `auth: 'offline'`, **`respawn: false`**, and `logErrors: false`; attach your own error/kick/end logging to stderr. Load pathfinder, attach event listeners, and wait for `spawn`, `waitForChunksToLoad()` with a timeout, health/inventory readiness, and a loaded solid floor plus body/head clearance. A connected login is not proof of ready chunks. [Loader defaults](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/loader.js), [health events](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/health.js), [chunk loading](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/blocks.js).
7. For reproducible spawn placement, record the baseline's surface position and teleport there only during setup. If needed, the observer can be spectator during baseline preparation, but switch to Survival, clear its inventory/effects/XP, reset personal state, and discard its exploratory memory before the ready observation. The pristine baseline should have full health/food, no carried inventory, no active burning/drowning, and no hostile within 16 blocks. A newly created player is simpler than repairing stale player NBT. Remove baseline-preparation playerdata/stats/advancements before the final login, while the server is stopped; let the fresh player spawn, then apply the recorded safe spawn and final time.
8. Hold controls neutral through setup. Confirm Survival, full health/food, empty inventory and unprivileged status, then emit the initial observation and start the monotonic 300-second timer. No invulnerability, teleport, give, weather/time adjustment, tick freeze, or admin mutation is allowed after this barrier. Read-only performance/audit queries are allowed outside the model interface.
9. During play, `observe()` returns the newest snapshot without stopping the world. Action requests are asynchronous; a compatibility `step(action)` may wait a bounded interval for a result/new snapshot, but is not a turn boundary. Death terminates; time limit truncates. Freeze score bookkeeping at that boundary before performing cleanup.
10. On finish, clear controls/cancel actions, close windows, disconnect the bot, send `save-all flush` and `stop` to the server, and wait up to about 20 seconds. Then terminate the owned process, followed by kill only if necessary. Await Node exit too. Preserve result, logs, manifest and optional final world; cap retained worlds to avoid disk growth. On hard shutdown mark the world unsafe for baseline reuse.

Use request/response barriers, not arbitrary sleeps, when setup commands require confirmation. Server stdout contains unrelated logs: correlate command output conservatively, or confirm the resulting bot state. Parent failure should also cause bridge/server cleanup (EOF/watchdog and process handles). A port race, startup crash, failed dependency load, or disconnected bot is an explicit infrastructure error, not implicit successful reset.

**Seeded scenarios and held-out evaluation.** Natural world generation varies terrain/resources but does not make mob AI, drop randomness, chunk scheduling or networking fully deterministic. Record this limit. Compare policies on matched seeds with repeat trials, identical dependency locks, server settings, limits and admission rules.

For the first benchmark, admit a safe dry surface spawn only when there are at least 12 harvestable log blocks in the nearby 48-block area and at least 24 ordinary stone blocks reachable by short shallow mining within 48 blocks; neither route should require crossing lava or a fall greater than two blocks. Use a fixed local geometric search, not policy success, to establish this. Choose candidates in a stable coordinate order around world spawn, within a fixed radius such as 128 blocks; stop after a fixed cap and mark an inadmissible seed explicitly. Do not silently replace a seed following agent failure. Keep coal/iron/animals optional: those variations test adaptation. Preparation can inspect privileged world data, but the policy may only see the normal initial local observation. Cache the admission result and frozen baseline under a configuration hash.

Split by **world seed**, not just repeat runs of the same map. Assign equal tick-1,000 and tick-9,000 starts using another digest component. Daytime and late-afternoon are not separate permission to alter weather/health mid-run. Keep Normal difficulty and clear initial weather in the baseline benchmark; rain/night-only starts or supplied equipment should be separately labeled variants. Changing the version, score weights, admission rules or time budget changes the benchmark ID.

**Observation contract: compact JSON, partial world knowledge.** Every message carries protocol version, episode ID, monotonically increasing sequence, monotonic observation timestamp, elapsed/remaining wall time, last server-time sample and freshness. Serialize finite numbers only; unknown = null or an explicit flag, never an invented zero. Convert selected fields from Mineflayer objects, not entire cyclic objects or BigInts.

| JSON group | Contents and provenance |
|---|---|
| `self` | Position, velocity, yaw/pitch, on-ground, health, food, saturation, oxygen if known, equipped items/durability, dimension, game mode, status effects. Coordinates are block units: +y up, +x east, +z south. Prefer look-at points to guessed yaw conversions. |
| `inventory` | Named item counts and slots, empty slots, held item, off-hand; explicit non-overlapping slot ranges. `bot.inventory.items()` is useful but check equipment separately when needed. Do not assume arbitrary entity health is exposed. |
| `world` | Daytime/weather and nearby loaded blocks/entities. `blockAt(Vec3)` may return null for missing data. Include target block name/position/state and last-seen time. |
| `candidates` | Bounded lists of resources, traversable stand positions, safe retreat waypoints and frontier waypoints with stable IDs. Code computes distance/path estimate, reachability, line of sight, tool eligibility, expected drops and hazard flags. |
| `entities` | Nearby entity ID/type/position/velocity and visible metadata relevant to threat/food. Include distance and closing rate calculated in code. IDs can disappear: validate every action against the latest entity map. |
| `workstations` | Remembered placed/seen crafting tables/furnaces with last-seen coordinates; furnace contents only when actually observed through a window, otherwise unknown/predicted with a label. |
| `task` | Active job, phase, progress, remaining deadline, candidate ID, pending cancellation and last error. Include recently failed/unreachable targets. |
| `progress` | Inventory high-water marks, latched milestones, score components, verified event history and action outcomes. Arithmetic belongs in code. |

Mineflayer's block cache contains server-sent chunks, which can include hidden blocks underground. Specify one observation policy and keep it constant. Recommended policy: include collision geometry needed for navigation, but surface resource candidates only when exposed to known air or directly visible; never supply an ore list obtained by scanning all hidden chunk interiors. Do not read world files or seed-derived maps to give the agent ore locations. This is structured client observation, not a claim of pixel-equivalence. The server is authoritative; cached observations can lag. [Block API implementation](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/blocks.js), [entity tracking](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/entities.js), [inventory operations](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/inventory.js).

Update the cache on `health`, `breath`, `death`, `entityMoved`, `entitySpawn`, `entityGone`, `playerCollect`, world block updates, inventory `updateSlot`, and path events. Physics remains internal at its normal cadence. Publish snapshots around 5 Hz plus urgent changes. Bound expensive block searches (initially radius 32, 16–32 candidates); incremental caching is preferable to scanning all loaded chunks on every tick. Keep server-age samples and client physics counts distinct; a local physics tick is not proof that the server advanced. [Physics](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/physics.js), [time](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/time.js).

**Action contract and concrete Mineflayer mappings.** Send request ID, episode ID, observed sequence, action name, validated arguments and deadline. A quick accepted response returns job ID; subsequent result events say succeeded/failed/cancelled and provide postconditions. Each ID is idempotent: a transport retry must not craft or place twice. Only one job owns movement/hands/window state at a time. A gather or furnace job can have phases, but do not run competing pathfinders or inventory transactions concurrently.

| Allowed action | Implementation mapping and required checks |
|---|---|
| `navigate(candidate_id)` | `bot.pathfinder.goto(goal)` or `setGoal(goal)`; use `GoalNear` for an open stand position, `GoalLookAtBlock(position, bot.world, options)` for a reachable visible block face. Goal coordinates are not necessarily the solid target block's occupied cell. |
| `look_at(point)` | `bot.lookAt(Vec3)`; bound coordinates and recheck possible Enderman gaze. Do not let a second controller continuously override pathfinder orientation. |
| `gather(block_candidate_id, max_blocks)` | Navigate into interaction position, re-read block, equip suitable tool, `canDigBlock`, `block.canHarvest(tool.type)`, `bot.dig(block)`, then collect the dropped entity and verify inventory. Cap batch size and stop on hazard/deadline. |
| `equip(item_name, destination)` | Find actual inventory item, then `bot.equip(item, 'hand' / 'off-hand' / armor destination)`. Refuse missing items; serialize with windows. |
| `craft(item_name, desired_output_count, table_id)` | Resolve item ID via `bot.registry.itemsByName`, find feasible recipe using `bot.recipesFor(id, null, desired_output_count, tableBlock)`, then craft the required operation count. A nearby **placed** table block is required for 3×3 recipes. |
| `place(item_name, reference_position, face)` | Equip, resolve a loaded reference block, call `bot.placeBlock(referenceBlock, Vec3 face)`. Face must be one of six unit vectors; destination is reference + face. Check support, reach, replaceability and self/entity collision; confirm resulting block. |
| `furnace_start(furnace_id, input, fuel, counts)` | `bot.openFurnace(block)`, await readiness/update, `putInput(type, metadata, count)`, `putFuel(...)`, close window. Fuel and ingredients must already exist. Return after loading; smelting continues asynchronously. |
| `furnace_take(furnace_id)` | Reopen; inspect `outputItem()`, `takeOutput()`, verify inventory and close. Do not award an item merely because a timer elapsed. |
| `eat(item_name)` | Equip actual food and `bot.consume()` with timeout; verify food/item change. Avoid window conflicts. Immediate hazard response takes precedence. |
| `attack(entity_id)` | Revalidate target, line of sight, melee reach and code-maintained weapon cooldown, then `bot.attack(entity)`. One attack command is not a full combat strategy or kill confirmation. |
| `shield(on)` | Equip shield off-hand; use `bot.activateItem(true)` / `bot.deactivateItem()`. Facing and activation delay matter. Coordinate with eating and hand ownership. |
| `cancel(job_id)` / `wait(duration)` | Cancel the owner and clear its controls. Wait is bounded; the safety controller continues. No free-form JavaScript, raw packets, console commands or creative inventory operations in policy actions. |

Crafting's `count` means **recipe executions**, not output items. For a four-plank recipe, requesting four output items requires one execution, not four. Code computes `ceil(desired_output_count / recipe.result.count)`, accounting for inventory/reservations and any desired-total versus desired-new convention. Use desired-new consistently in the action schema. `recipesFor` finds currently feasible recipes; `recipesAll` can support a prerequisite planner but is not proof of material availability. Craft Promise completion must be followed by inventory confirmation before credit. [Craft implementation](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/craft.js).

Smelting is **not** a crafting-grid recipe. Furnace windows provide input/fuel/output and progress updates; progress may initially be unknown. Close windows when finished transferring and reopen to retrieve results. Never hold the inventory lock for the entire cooking period; record a workstation task and do nearby useful work. [Furnace implementation](https://github.com/PrismarineJS/mineflayer/blob/4.39.0/lib/plugins/furnace.js).

**Navigation, cancellation and deadlines.** Start with conservative movement settings: `canDig=false` for travel, `allow1by1towers=false`, `allowParkour=false`, `allowSprinting=false`, `maxDropDown=2`, `infiniteLiquidDropdownDistance=false`; retain `dontCreateFlow` and `dontMineUnderFallingBlock`. Exclude lava, fire, cactus, magma, powder snow, hazardous berry bushes and unknown landings; prevent path placement by an empty scaffolding set/placement exclusion. Allow explicit, bounded gathering to dig its selected block rather than giving the travel planner unlimited permission. Escape may enable sprint only when food permits and a verified route exists. [Movement properties](https://github.com/PrismarineJS/mineflayer-pathfinder/blob/2.4.5/lib/movements.js).

Pathfinder's tagged defaults include 5,000 ms total search and a 40 ms per-tick computation budget. Start with shorter local goals and perhaps a 5–10 ms search slice, then measure event-loop lag. A path timeout/noPath is recoverable: blacklist briefly, try another stand position/target, or choose a frontier. A stalled job should not consume the whole episode. [Pathfinder implementation](https://github.com/PrismarineJS/mineflayer-pathfinder/blob/2.4.5/index.js).

Suggested deadlines: navigation 10–15 s per segment, placement 5 s, equip/food 5 s, craft 10 s, dig `digTime + margin` bounded by the job budget, pickup 3–5 s. These are tuning values. A completed dig is not a completed gather; report `no_drop`, `inventory_full`, `unreachable`, `target_changed`, `missing_materials`, `hazard`, or `timeout` precisely.

Do not implement cancellation as just `Promise.race` against a timer: that leaves the losing action running. Cancel pathfinder via `setGoal(null)` for immediate goal removal; `stop()` normally waits for a path node. Stop digging, deactivate item use, clear owned movement controls, close a window when safe, invalidate the job token, and wait for asynchronous completion handlers to settle. A superseded job must never resume and overwrite a newer command. Add an independent safety heartbeat every 50–100 ms so a slow model or stuck action cannot hold forward into danger.

**Python–Node transport.** Use newline-delimited JSON on Node stdout/stdin; logs and Java output go elsewhere. Mineflayer's default error logger may write to stdout, hence `logErrors:false` plus explicit stderr handlers. Both ends must continuously drain streams, bound message sizes and validate schemas. Response kinds: ready, observation, accepted, action_result, terminal, infrastructure_error. Parent requests: reset/start handshake, observe, act, cancel, close. Server management stays in the Python parent and is not exposed to policy JSON.

Astra and Jev requests run asynchronously outside Node's physics event loop. Every model reply references an episode/observation/plan ID and expiry. Revalidate the chosen candidate against current state; reject results from earlier episodes or obsolete jobs. Jev receives legal candidate IDs and derived flags, never a demand to compute recipes, distances or scores. Priority: deterministic imminent-danger reflex → valid Jev choice within Astra's approved options → prior plan continuation → safe stop/shelter fallback. A stale-reply threshold around one second is a starting point for tactical choices; no timeout makes stale advice safe automatically.

**Scoring implementation, reproduced here so this document is sufficient alone.** At every server-confirmed personal inventory update, sum each resource category across personal slots and update its episode maximum. Exclude crafting previews, cursor and external containers; count armor/offhand once. Resource points: `min(logs_max,10) + 0.5*min(cobble_max,20) + min(coal_plus_charcoal_max,5) + min(raw_iron_max,5)`, maximum 30. Logs are the eight unstripped Overworld species in 1.21.1; cobble is precisely `cobblestone`.

Latch first verified possession: crafting_table 5, wooden_pickaxe 5, stone_pickaxe 10, stone_axe 5, furnace 5, torch 5, any cooked-food item 5, iron_ingot 5, shield 5 (maximum 50). Cooked-food whitelist: cooked_beef, cooked_porkchop, cooked_mutton, cooked_chicken, cooked_rabbit, cooked_cod, cooked_salmon, baked_potato. Legitimate loot counts. Add `10*alive_seconds/300` and, only at an alive time-limit finish, `10*health/20`; subtract 20 on terminal death; clamp total to [0,100]. Use the configured episode duration in place of 300 only for a separately labeled configuration. Preserve high-water/milestone credit after spending items. Do not count commands, attempted actions or predictive inventory previews as success.

Maintain the evaluator's authoritative result independently of model output. Client inventory libraries can update local windows optimistically; use settled server slot/window acknowledgements and postconditions for credit. Keep packet/event audit timestamps and corroborate final inventory/stats with server-side data during validation. A dropped/recollected item or workstation picked up twice must not earn duplicate credit. Score is absolute; optional dense reward is its difference and can be negative at death. Also report milestone times, health, survival fraction, action failures, progress component, server lag and invalid-trial reason. Separately listing progress prevents idle survival points from disguising a weak policy.

**Required validation before accepting the adaptor.** These tests belong to the implementation phase, not this study.

1. Install/import under Node 26 and wrap using the exact evaluator Python 3.14.5. Confirm no default Microsoft login, cached credentials or GUI prompt. Start and stop the pinned server twice without leaving children or sockets.
2. On a disposable known fixture, verify chunk readiness, walking/up/down one block, cancelling movement, hand-mining a log, drop pickup, planks/sticks/table crafting, table placement, wooden pickaxe, stone harvest, stone pickaxe and furnace. Verify inventory quantities, tool suitability and one recipe execution yielding multiple outputs.
3. Exercise fuel insertion, genuine furnace waiting, taking output, eating, immediate cancellation, death without respawn, and a 300-second wall timeout. A fixture may use administrative setup before its test begins; evaluated play may not.
4. Test missing chunks, wrong tool, out-of-reach/occluded block, no path, changed target, full inventory, missing ingredients, cancelled window transaction, stale model reply and lost bridge. No unbounded wait or continuing cancelled job.
5. Reset the same baseline twice and check initial inventory/health/time/position/terrain manifest and zero score. Ensure a previous episode's placed/missing blocks, inventory and latched milestones do not carry over.
6. Check the score against hand-calculated inventory traces, including spend/drop/reclaim/equip/window-preview cases. A full healthy idle run scores 20; all resource caps plus all milestones and a healthy finish scores 100. Infrastructure failures are recorded separately.
7. Run several natural admitted seeds, including dusk and uneven ground, to measure TPS/event-loop lag and actual startup/action latency. If a dependency pin fails, record the failure and replacement pin and rerun the affected checks; never claim source compatibility alone is a passing smoke test.

**Material risks.** Current shell DNS restrictions can block all installation; JDK/server downloads can be large; world generation and retained snapshots cost CPU/disk; latest library transitive releases can regress historical protocol behavior; physics/pathfinding may stall on water, doors or irregular terrain; server statistics and client state can lag; the same world seed does not freeze all gameplay randomness. Current Mojang terms apply, and neither server software nor a modified client/server should be redistributed as part of the harness. No public-server anti-cheat interaction or external hosting is part of the selected design.
