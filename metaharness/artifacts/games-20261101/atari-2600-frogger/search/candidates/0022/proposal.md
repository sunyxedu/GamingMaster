# Candidate 0022 — Viability search with a latched vertical carrier exit

**Parent:** `candidates/0019/`. I retain the parent’s one-hop/neutral-rearm control principle and observation-based road/river forecasts, but replace its route-selection and emergency bridge with a fresh bounded viability search and a carrier-row exit controller. The experiment is informed by the best reference `0017` and the drift-watchdog experiment `0020`; it does not alter either candidate.

## Hypothesis and concrete evidence

The remaining losses suggest two failures that are coupled by the action bridge: a route can regard a wide carrier interval as safe while the frog drifts toward its edge, and a same-row lateral rescue can keep the frog exposed to the same carrier/actor interaction. Increasing a scalar clearance margin has already been refuted (`0015` made 752 margin-based overrides but still had 33 gate failures). `0019`'s commitment and actor response likewise did not reduce failures: it averaged 5.67 deaths and 42.5 homes, and seed 107 lost lives on row 8 at ticks 20444 and 21084 after `NOOP` from x154 with a shape-184 turtle contact and the auxiliary actor at x138/140. The saved plan at tick 20424 was `NOOP`, margin 27.5, forecast endpoint x148. This is a concrete case where a large geometric margin hid an unsafe passive ride at the screen boundary.

`0017` also died on row 8 at tick 16280 with frog x100, auxiliary x108, a safe-looking turtle, and `NOOP` (plan margin 3.5); a second identical x100/x108 loss occurred at tick 26514 (margin 6.5). Its row-8 loss at tick 22094 was frog x148 / actor x132 despite a `RIGHT` plan with margin 24.5. `0020` added measured frog drift, but its seed-109 trace shows repeated edge emergencies on the same row and alternating lateral actions: around ticks 22223–22306 it switched among RIGHT/LEFT on row 8 as the frog moved near x128–147, with projected x141–157 and future support alternately `stable`/`lost`. This suggests its counter-steering intervention can become a same-carrier oscillation rather than an exit.

**Testable hypothesis:** under a moving-carrier edge or actor threat, the controller should first seek a currently supported vertical transition to another row. A vertical hop exits the current carrier/actor row; repeated lateral corrections do not. Latch the chosen vertical direction across subsequent river rows while the threat remains, revalidating support each time. Use lateral correction only if no safe vertical exit exists. At all other times retain the route search, but use a distinct dynamic-programming viability search rather than the parent’s same route portfolio implementation.

## What changed

1. Rebuilt the small moving-object forecast and bounded search. The search keeps diverse spatial/time states and scores complete road-to-river launch or river-to-home routes, using decoded object copies, measured per-object speeds, safe carrier spans, local home-alert matching, and a separate auxiliary actor overlay. On the road it takes a live-certified forward hop whenever that landing is open, otherwise it uses the central launch corridor; this avoids letting a long-distance bay preference keep selecting sideways pulses. When the median has no current complete river/home route, it waits only if the current median position passes the live check. The current observation is rechecked before posting.
2. Added a rider-risk estimate based on observed frog motion while `moving_with_platform` is true, plus the active same-row auxiliary candidate and projected carrier edge. This is an execution warning, not a claim that a carrier forecast proves survival.
3. Added a **vertical-first, latched exit** for the threatened river row: test UP/DOWN against one-frame landing and short release support, prefer a verified forward exit, then a backward exit, and only then a verified interiorward lateral step. Preserve the selected escape direction across row transitions while the threat remains and each repeated move passes live support validation; clear it when the threat disappears, the frog loses a life, or geometry invalidates the move. Jev's accepted typed escape preference can reorder only these already-verified choices. This directly tests whether sustained row exit outperforms `0020`'s repeated same-row corrections.
4. Keep standard-mode debounce: send a direction pulse, wait for observed movement or a four-frame cap, and rearm with NOOP. Death/home animations do not trigger navigation.
5. Keep Jev/Astra advisory. Neither model may invent a joystick action or disable geometry. Code-owned fallbacks remain executable if calls are late, malformed, or low-confidence.

## System-1 state, questions, thresholds, and bridge

Each Jev request carries strict JSON with: `epoch` (deaths, frogs_home, level), `phase`, `row`, `x_band`, `timer_band`, `homes` (bay ID, upstream, committed, matched alert, complete route), `committed_bay`, `actor` (same-row and derived near/far), `carrier_risk` (threat, edge, actor), and a compact `recent_loss_class`. Rules explicitly say that unknown crocodile state is not safety evidence, Jev chooses a whole-crossing preference rather than a frame action, and a threatened carrier should leave the row vertically if code verifies support.

The batch asks two reversed-order `Choice` pairs and a `Noul`:

- `bay` / `bay_check`: select an open, unalerted whole-crossing bay. Accept only if they agree, the selected-option probability in both answers is at least **0.70**, the response is at most 75 game ticks old, the life/home/level epoch and derived risk signature are unchanged, and the bay is still open. This adjusts the initial commitment while on the road; river route selection remains code-owned and only a currently complete route can set the target.
- `escape` / `escape_check`: select UP, DOWN, INWARD, or KEEP from the explicit current carrier-risk facts. Accept only if the reversed choices agree and each selected-option probability is at least **0.75**, with the current epoch, risk signature, and response age (<=75 ticks) still valid. The result only breaks ties among code-generated verified exits; it cannot authorize an unsafe move. Jev's selected UP/DOWN can order verified row exits, and INWARD can prefer a checked lateral move for actor-contact risk; a missing or late answer leaves vertical-first code control intact.
- `review`: request an asynchronous Astra protocol review only at probability **>=0.85**.

One Jev request may be outstanding. Schedule about every 90 ticks normally and every 24 ticks while a carrier threat is present; use a 3-second timeout, catch ordinary call/output failures, and keep acting from the code planner during the call. The 0.2-second typical response is not on the movement critical path. Astra receives recent loss witnesses and may return only the bounded `itinerary` and `escape` policy enums. It is scheduled sparsely after a witnessed loss, uses a 100-second timeout, and is accepted only against the same failure revision. Invalid text preserves the current policy.

## Fallback, freshness, and lifecycle

A route action must pass the latest one-hop geometry check. On a threatened carrier, the emergency tests short-horizon support for row exits before lateral movement; if no checked escape exists, it falls back to the ordinary guarded route rather than inventing a hop. Every direction is explicitly rearmed. Stale model advice is discarded, and timers, score, and positions are computed by code rather than asked of Jev. The loop runs until `game.done`/`ctx.done`; it does not stop at an internal action count. Contract lifecycle exceptions propagate; expected timeout, malformed text, and malformed answer payloads leave code control intact.

## Confirmation and refutation

Confirm if traces show that carrier/actor warnings more often produce supported row transitions, fewer repeated LEFT/RIGHT escape alternations on one row, fewer row-8 edge/actor deaths (especially the x154 / x100-versus-108 witnesses), more homes per life, and no increase in water deaths or no-route stalls. Compare score and deaths, not the number of emergency events. Refute if the supposedly supported UP/DOWN exits cause more water/diving deaths, if the latch repeats an exit after its threat has passed, if it fails to activate before the demonstrated edge/actor contacts, or if score/homes decline without a corresponding reduction in deaths. The model contribution is separately visible through accepted-choice and action-preference logs; call volume alone is not evidence of benefit.

This is a single, falsifiable controller change, not a claim that the noisy carrier decoder is an exact collision oracle or that any positive route margin certifies survival.
